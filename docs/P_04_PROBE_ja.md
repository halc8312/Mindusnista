# P-04: 生成・削除・命令を伴う配列状態の比較

更新日: 2026-09-10。開発用の独立モデルを `tools/pythonista_dynamic_state_probe.py` に追加した。
ゲーム本体、P-01/P-02/P-03、0.1.2-dev、ゲーム保存schema 1には変更を加えない。
機能・規模・エフェクト品質・原作iOS/Steam保存共有は引き続き完全移植の要件である。

## 実行

Python 3.10互換の単体 `.py`。標準ライブラリと、すでに入っている場合だけNumPyを使う。
pipや別のソースファイルは不要で、Pythonistaへこのファイル一つを置いて実行できる。
引数なしは初期20,000件、初回1＋warmup2＋steady7回、その後1回のJSON保存復元と3tick続行。
ゲーム本体を置き換えるファイルではなく、ゲーム保存や原作`.msav`も読み書きしない。

```sh
python tools/pythonista_dynamic_state_probe.py --count 20000 --warmups 1 --repeats 5 --output p04-20000.json
python tools/pythonista_dynamic_state_probe.py --count 200000 --warmups 1 --repeats 5 --output p04-200000.json
```

初期0件も有効。正常な件数を小さく切り捨てる独自上限は設けない。
メモリ不足などの実行例外は失敗として記録するので、任意の規模で完了する保証ではない。
NumPy不在または`--no-numpy`は3条件を`not_run`、全体を`partial`とする。
NumPy内部の欠損・壊れたimportは`error`、比較不一致・途中例外・終了処理例外は全体`failed`。
正しい比較・保存復元・終了処理が完了した条件だけにPythonとの時間比を付ける。

JSONは指定した新しいパスに保存し、既存ファイルは上書きしない。省略時は標準出力へJSONを出す。
日本語要約は標準エラー。全体failedは終了コード1、出力作成・書込・flush・close失敗は2。
書込後のcloseで失敗した場合も「保存成功」の表示を出さない。

## 全条件に共通の動的モデル

各個体はint64のIDとfloat64のx/y/vx/vy/target_x/target_y/threshold²を持つ。
外部から渡す共通の命令リストを順番に適用してから、全生存個体の位置を`x += vx; y += vy`で更新し、
更新後の距離二乗と閾値判定を計算する。生成した個体もそのtickから更新し、削除した個体は更新しない。
命令は同じIDへの複数命令も順に反映し、後の速度・標的指定が先の値を置き換える。

| 命令 | 効果と検証 |
|---|---|
| spawn | 全8値を持つ行を追加。有限float、非負threshold²、未使用のint64 IDを要求 |
| delete | 存在するIDを削除し、そのスロットを空きリストの末尾へ返す |
| velocity | 存在するIDのvx/vyを更新 |
| target | 存在するIDの標的x/y/threshold²を更新 |

IDはfloatへ変換しない。初期IDの重複は禁止。初期配置は入力順を維持する。
新規IDは`next_id`以上である必要があり、生成後は`next_id = ID + 1`とする。
`next_id`の初期値は初期最大ID＋1と0の大きい方。ID自体は符号付きint64を受け入れる。
削除後もIDは再利用せず、スロットだけを再利用する。範囲末尾を使った後の新規生成は明示的に拒否する。
この規則はモデルの仕様であり、原作のID割当規則の移植を意味しない。

結果の順序は生存個体の挿入順。新しい個体は末尾に入り、物理スロットの再利用で順序を変えない。
各tick、**ID・x・y・vx・vy・標的x・標的y・threshold²・距離二乗・真偽の全10列**を、
全生存個体分の独立したPythonリストへ返す。次tickの更新や出力側の変更は過去の結果へ逆流しない。
配列を保持しても、この比較では全結果のPythonオブジェクト化を計測から外さない。

命令batch全体を適用前に検証する。触れたIDだけの一時的な存在状態を使い、batch内の生成→更新も認識する。
途中の未知ID、二重削除、削除後の古い命令、再利用ID、不正値、未知フィールド等は、batch全体を変更前に拒否。
命令処理中・更新中・worker中の資源例外は取り消し成功と装わず、runnerを失敗状態にして
以後のstep/保存を拒否する。すでに開始したworkerは、submit/結果受取の途中例外でもすべて完了まで待つ。

## スロット保持・成長・計算

両条件ともID→スロットの辞書、挿入順、LIFOの空きスロットを保持する。
初期容量は初期件数と同じ。空きがなくなると容量を倍増し、0の場合は1にする。
既存の状態を維持し、NumPyでは既存数値を新配列へ全件コピーする。増えた領域から小さいスロット順に
割り当て、削除で返ったスロットは先に再利用する。
容量を縮めたり、上限到達時に個体を落としたりはしない。容量増加とコピー時間は命令適用区間に含む。

| 条件 | 数値保持と仕事 |
|---|---|
| Python / 1 | 行のスロットリストと距離/判定バッファを保持。容量を走査してNoneの空きスロットを飛ばす |
| NumPy / 1・2・4 | int64 ID配列、float64状態/作業配列、bool判定配列を保持。容量全体を配列演算し、空きのゼロ領域も計算する |

NumPyは主スレッドで位置を更新し、距離・判定を非重複の容量区間に分けてThreadPoolExecutorへ渡す。
1ワーカーにも同じsubmit/同期経路を使う。結果反映で挿入順のスロット索引を作り、全列を`tolist`する。
計算バッファ・配列は成長時だけ再確保し、worker完了前に成長・次の命令・次の更新を始めない。
空き領域の余分な計算を含むため、容量と生存件数を併記する。ワーカー数を並列CPU実行の証明にしない。

通常の共通入力は最初のtickで生成を増やして成長を必ず起こす。次から削除と生成を繰り返し、
空きスロットを再利用しつつ、存在するIDの速度と標的を更新する。
全命令は一度共通生成し、SHA-256とtickごとの命令種別件数を記録する。生成時間は条件ごとのtick時間とは別。
モデルの生成数・頻度・ID方針を原作ゲームの制限や仕様には流用しない。

独立した辞書主体のScalarOracleが、runnerの更新・命令適用コードを呼ばずに同じ命令を実行する。
初回・warmup・steady全tickについて全10列の件数、順序、型、値を完全一致で照合する。
actual/expectedのdigestも別々に算出する。不一致は実際のdigest、不正出力で生成不能なら`null`を残す。
比較の途中例外では未完了sampleだけを先に追加せず、sampleと両digest列を常に同じ件数にする。

## 計測範囲

`time.perf_counter`による実経過時間。steadyのp50/p95/最大と全標本を記録する。
p95はnearest rankであり、steady5回なら最大値になる。短い共有PCの結果で持続負荷の達成を判定しない。

| 項目 | 含む処理 |
|---|---|
| dataset_seconds | 共通の初期値生成。別記録 |
| command_generation_seconds | 計測tick＋復元後3tickの共通命令生成。別記録 |
| prepare_seconds | 初期状態検証・取込・各配列/リスト・辞書・バッファ・executor確保 |
| initial_conversion_seconds | prepareの内数。初期状態取込と保持領域確保 |
| command_validate_seconds | 全命令の構造・値・IDの順序検証 |
| command_apply_seconds | 全命令の順次反映、削除・空き再利用・必要な容量成長 |
| mutation.growth_seconds | 容量成長の内数。command_applyへ二重加算しない |
| state_update_seconds | 容量走査による全生存個体の位置更新とtick加算 |
| compute_sync_seconds | 全距離/判定。NumPyはsubmitと全future完了待機を含む |
| result_apply_seconds | 挿入順で全10列をPythonリストへコピー・反映 |
| runner_overhead_seconds | 内部区間外の呼出し・計測辞書・戻り処理 |
| total_seconds | step呼出しから戻るまで。上記6区間の和 |

`mutation.free_slot_allocations`は「成長せず既存の空きリストから割り当てた回数」であり、
削除したスロットの再利用だけでなく、前の成長で確保した未使用領域も含む。
`capacity`と`active_rows`も各標本に保存する。削除したスロットの実再利用は回帰で別に確認する。

初期準備＋全計測tickを完了数で割った償却値、NumPy importを一度加えた値、
1回の保存復元を加えた値を別々に記録する。初回worker起動は初回tickに含む。
共通入力/命令生成・参照計算・全件照合・digest・報告作成・終了処理はtick時間外。
固定順Python→NumPy1→2→4で参照検査が交互に入る影響がある。
P-03は固定個体数・出力5列、P-04は動的命令・容量管理・出力10列で仕事が異なる。
**P-03/P-04間の時間比を同じ仕事の改善倍率として扱わない。**

## 共通JSONの保存と復元

比較器専用形式`mindusnista-p04-synthetic-state`/schema 1で、次をすべて保存する。
ゲーム保存schema 1とは別の形式である。

- 全容量分のslots（生存行の全8値、空きはnull）とcapacity。
- 生存IDの挿入順order、LIFOのfree_slots、次のIDの境界next_id、完了tick。
- format/schema/columns。ID→スロットの辞書は全slotsとorderから欠落なく再構築する。

UTF-8 JSONへの実encode、実decode、重複キー・型・有限値・ID重複・order・free_slotsと
slotsの整合性検証、同じバックエンドの新規確保と復元を実行する。
保存bytesを参照と完全一致で照合し、復元直後の内部状態、その後同じ外部命令3batchを再生した
全結果・最終内部状態まで比較する。free list順序やnext_idの欠落で続行が変わる問題も検出する。
外部命令列は呼出側が同じ続きから再送する契約で、snapshotに将来命令や外部の乱数生成器は含めない。

state_export/json_encode/json_decode_validate/state_restoreの4区間と総時間を記録する。
ディスクI/O・終了処理・原作codecは含まず、復元後3tickの検証標本は別のresume_samplesに記録する。
復元executorの遅延スレッド起動も最初のresume sampleに含まれる。
全計測7tickで1回保存復元する例の償却はその頻度に限った費用であり、実ゲームの保存周期ではない。

NumPyの保持数値バッファ概算は容量×81バイト。辞書・空きリスト・入力・結果・参照・JSON、
結果索引・一時配列・成長中の旧新領域の重なり・executor等を除く。**実ピークメモリは未測定**。

## レビュー後のPC実測

Linux x86_64 / CPython 3.12.14 / NumPy 2.3.5。各条件初回1＋warmup1＋steady5tickと、
1回の保存復元＋同じ外部命令3tickを実行。最終ソースSHA256:
`beae51b2ea4ee22890977048fd8a4ba87938c70d5f3058b174ebab1d33612ddf`。
測定前に他担当のローカル検査を止めたが、共有PC自体の負荷・周波数・GC等の影響を排除した試験ではない。

| 条件 | 初期20,000件 tick p50 / p95 | 初期200,000件 tick p50 / p95 | 初期200,000件 保存復元 |
|---|---:|---:|---:|
| Python / 1 | 20.459 / 36.921 ms | 247.634 / 277.331 ms | 2,382.167 ms |
| NumPy / 1 | 6.989 / 24.510 ms | 81.800 / 95.785 ms | 3,402.679 ms |
| NumPy / 2 | 6.787 / 7.386 ms | 162.712 / 183.813 ms | 3,233.052 ms |
| NumPy / 4 | 8.758 / 11.011 ms | 98.379 / 268.000 ms | 1,643.093 ms |

全条件で全10列・ID順・保存bytes・復元後の内部状態が一致した。
初期200,000件では生存件数206,249～206,250、容量400,000、計測7tickの命令は合計87,500。
初期20,000件では生存20,624～20,625、容量40,000、命令8,737。いずれも最初に拡張1回が発生する。
保存には空きslotや順序も含み、各条件のJSON bytesはそれぞれ1,979,817 / 20,411,016で同一だった。

この観測では初期200,000件のtick中央値はNumPy1が最短だったが、NP2/4を含め大きなばらつきがある。
1回の固定順・短い測定から最適ワーカー数や原因を断定しない。
NumPy1の区間中央値は命令検証13.936ms、命令適用9.066ms、位置更新3.470ms、計算同期4.252ms、
全結果反映50.955ms。総時間の中央値と区間中央値の和は同じ標本ではない。
数値計算の外にも費用が残り、NumPy1の保存復元はPythonより遅い観測だった。

初期200,000件のNumPy1は準備456.272ms、準備込み償却155.449ms/tick、
7tickに保存復元1回を含む償却641.546ms/tick。Pythonは674.586ms、389.102ms/tick、729.411ms/tick。
NumPy4は463.281ms、203.015ms/tick、437.742ms/tick。上記償却はNumPy importを含まない。
異なるバックエンドの最短tickと最短保存を組み合わせた架空の性能値は作らない。

これは動的な独立モデルの結果であり、ゲームのFPS、iPhone性能、原作float32、実msav互換の結果ではない。
