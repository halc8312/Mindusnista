## 確認した原作と変更範囲

今回、固定コミットの実ファイルを再取得して確認した。

  `offload`、`incrementDump`、`handleItem`、`produced`。
- [Drill.java](https://github.com/Anuken/Mindustry/blob/c9686eb5d0ae5dd47ee02c40f99f7d5018ccbc8c/core/src/mindustry/world/blocks/production/Drill.java):
  `DrillBuild.updateTile` の定期dump、生産前の容量判定、生産回数、最後の剰余処理。
- [ItemModule.java](https://github.com/Anuken/Mindustry/blob/c9686eb5d0ae5dd47ee02c40f99f7d5018ccbc8c/core/src/mindustry/world/modules/ItemModule.java):
  `add`、`write`、`read`。在庫はJavaの整数で、`add` 自体に設備容量の判定はない。

`World.offload` と `_tick_drill` の生産完了部分、そこから生じるドリル在庫の保存検証を変更した。
通常の設備容量、新設備、描画、操作、タイマー、更新スケジューラーは今回の変更範囲に含まない。

| 規則 | 固定原作と今回の挙動 |
|---|---|
| 生産品の搬出先 | 呼出開始時のcursorを起点に、明示した近隣順で1周まで試す |
| cursorの更新 | 各近隣の受入判定より前に1回進める |
| 外部への搬出成功 | その相手へ新しい1品を渡す。元からある自分の在庫は減らさない |
| 全拒否・近隣なし | 新しい1品を自分の在庫へ必ず追加する。ここに容量判定はない |
| 定期搬出と生産 | 定期dumpを先に呼び、その後で生産開始の容量を判定する |
| 複数の生産完了 | 容量をループ前に判定し、完了した全数を搬出する。個々の品の間では容量を再判定しない |
| 進捗の剰余 | 完了分の搬出後に `progress %= delay` を行う |

旧実装では近隣の受入成功後だけcursorを変更し、全拒否時の自分への追加は呼出側が担っていた。
また、生産ループの各回で容量を再判定していたため、在庫9・完了3個・搬出先が拒否、という
条件で2個の完了分が失われた。今回の結果は在庫12、生産統計3となる。
容量10は引き続き**次の生産を開始できるか**の判定に使い、12を10へ切り捨てない。

`World.offload` の戻り値は開発版固有の観測用boolとして残した。Trueは外部搬出、Falseは
自分の在庫への追加を意味する。Java原作のoffloadはvoidであり、このboolは原作APIではない。
`stats["mined"]` は従来どおりローカル生産統計。原作の `produced` が担う
キャンペーンの生産記録・アンロック・ネットワークの処理を移植済みとは扱わない。

## 同じ拒否を大量に繰り返さない

schema 1は以前から大きい保存progressを許容している。容量ごとの打切りだけを外すと、
拒否先へ何億回も同じ搬出を試す経路が生じるため、**最初の全拒否以降の残り**を算術でまとめる。

1. 外部へ渡せる間は1個ずつ、原作順で実際の `receive` を実行する。
2. ある1品について全近隣が拒否したら、その1品はoffloadが自分へ追加する。
3. 残りの完了個数を同じ品の在庫と生産統計へ一括加算する。進捗の剰余は最後に計算する。

根拠は現在の同期的なWorldに限られる。拒否した `accepts` / `receive` は状態を変更せず、
同じ生産ループの途中にはtick・近隣変更・別命令が入らない。受入条件は搬出元の在庫数や
生産統計を参照しないため、最初の全拒否後の同品目もすべて拒否される。
1周失敗後のcursorは既に正規化済みで、その後に同じ1周を繰り返しても最終値は変わらない。
近隣なしの場合はcursorを変更しない。

この処理は数や機能の上限ではなく、同一結果になる拒否の反復をまとめる処理である。
副作用を持つMODの受入処理、再入・非同期の近隣変更などには、この証明をそのまま適用できない。
その機能を導入するときは集約可能な条件を改めて判定する必要がある。

回帰では保存progress `10**12` から1,538,461,538個の完了を計算し、閉塞先への受入呼出は1回、
在庫・統計・進捗・cursorは完了分を保存することを確認する。先に受入成功がある構成も含む。
これは算術と処理回数の検査であり、iPhoneのFPSや大規模工場の性能測定ではない。

## schema 1の継続

保存フィールドやschema番号は増やしていない。以前の正常な保存を引き続き読み、
同じ保存progressから完了した全個数を処理する。

新しく到達できるドリルの容量超過在庫を復元するため、ドリルだけは既知の品目かつ
厳密な正整数を受け付け、従来の各品目10・合計容量以下の検査を適用しない。
bool、0、負数、浮動小数、文字列を拒否する。ルーターの容量1、未対応設備の在庫拒否等は維持する。
固定された新しい小容量上限を設けず、整数の値を品数ぶんのオブジェクトへ展開しない。

Pythonの整数と原作のJava int32は異なる。今回のJSON在庫拡張は、Javaの整数オーバーフローや
原作 `.msav` の符号付き整数codecを再現する変更ではない。
保存ファイルの既存byte制限、他のフィールドの既存検証は別の課題として残る。
容量を超える新しい保存は旧スクリプトには読めないため、更新前の保存を退避しておく。

## 比較器が確認する境界

`reference/DrillOffloadReference.java` は原作メソッドを抽出し、
`tools/check_offload_reference.py` が同じfixtureを実際のPython `World` へ渡す。
fixtureは22ケース・44明示呼出し。これはunittestメソッド数ではない。
近隣の配列と受入可能な品目・容量は明示したテストアダプターであり、原作工場本体ではない。

- 直接offloadでは、すべての試行順・受入前cursor・結果・自分の在庫・相手の在庫を厳密比較する。
- 生産tickでは、全生産数・最終在庫・相手の全受領数・cursor・進捗を比較する。
  定期dumpの全試行、最初のoffloadの試行と生産前剰余の順も比較する。
- 生産イベント名で連続するoffloadを一つにまとめる。集約で意図的に省略した
  2回目以降の失敗試行の呼出回数は比較対象にしない。Java側は小さいfixtureで元のループを実行する。
- 乾式・効率1・delta1、銅／鉛・明示した鉱床数で試す。fixtureの進捗は小さい整数とし、
  対象の進捗・個数を厳密比較できる条件へ限定する。

別のPython回帰では、本物のドリル→ベルト→ルーター、複数搬出先の順序、貨物保存、
旧schema 1からの生産と容量超過後の保存再開を確認する。
これは原作の配置履歴に依存するproximity順、EntityGroupの削除・sleep復帰、全scheduler、
タイマー位相、液体・効率・全鉱石、float32全体、効果、キャンペーン、原作ファイル互換を確認するものではない。

`python tools/check_project.py` はPC側検査、Java比較には動作するJDKが必要。
JDKが使えない場合は比較器がexit 2で未実行を記録する。**0.1.2の実機成功は未報告のまま**。
