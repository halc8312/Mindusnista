# 完全移植へ向けたロードマップ

これは実装計画であり、完了の宣言や工数保証ではありません。
対象は Mindustry v159.7。最新版追随は別の変更として扱い、途中で基準を混ぜません。
原作の全ファイル・全コンテンツを棚卸ししてから、対応表の分母を決めます。
「完成率 80%」など、分母と根拠のない数値は使いません。

## 状態と完了判定

機能ごとに「未調査／未実装／暫定／原作計算部移植／統合比較済み／実機確認済み」を記録。
それぞれに対象バージョン、比較方法、未対応条件を添えます。これらは常に一直線の段階ではありません。
例: 新規 UI が実機で動いても、原作戦闘の互換性は上がりません。

「遊べる開発版」「対象サブシステムの互換版」「対象原作版の完全移植」を別の名称にします。
MOD やネットワークを未対応のまま、単に完全版と名乗らないこと。

ID は分類です。依存関係に応じて進め、ファイル形式・通信・ID 設計を M7/M8 まで放置しません。
M0 を際限なく整備するのではなく、配布・分割の最小限を終えたら M1 の移植へ戻ります。
原作の統合 oracle がすぐ動かない場合、何を実行したかを明示した抽出参照で一段ずつ範囲を広げます。
抽出した自作 Java を原作本体の実行結果と呼ばないこと。

## 最初の輸送比較候補

直線ベルト、90度の曲がり、左右からの同時流入、詰まりと解除、ドリル→ベルト→コア、
ルーターの近隣順、荷物を持つ建物の回転・撤去・保存再開。
対象ファイルを固定版から実際に読み、`minitem/mid/lastInserted`、`offload/dump`、
タイルのアンカー、エンティティ更新順を確認してから fixture を設計します。
単に暫定実装の出力を期待値にして、原作互換テストと名付けないでください。

## 全段階で守る条件

iPhone は標準 Pythonista 環境で起動できること。実機のフレームレート・メモリ・発熱は
PC の値で代替せず、対象機種と工場規模・測定条件を記録します。
目標性能は実測後に設定し、達成のためにゲームルールを黙って変更しません。

既存 MOD を動かすことと、Python で自作改造をできるようにすることは別々の目標です。
Java/JS 互換や大規模マップの速度は現在保証していません。実行方式を検討・試験し、
不確かな点と具体的な障害を記録しながら進めます。
