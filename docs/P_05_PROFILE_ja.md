# P-05: 実際の World の処理時間と保存続行を測る

`tools/profile_world.py` は、配布本体 `mindustry_pythonista.py` の **実際の `World.step()`** を測る開発用ツール。
P-01～P-04 の独立数値モデルから、本体で高速化すべき処理を選ぶための測定へ進む。
この測定ツール自体はゲーム本体、原作基準 v159.7、0.1.2-dev、保存 schema 1、既存の制限・描画・ルールを変更しない。
原作の全システム、Pythonista の scene/UI、iPhone 性能を検査するツールではない。

## 実行

リポジトリ直下で、未使用の出力名を指定する。

```sh
python tools/profile_world.py --preset small --scenario all --ticks 60 --warmups 5 --output world-profile-small.json
python tools/profile_world.py --preset standard --scenario all --ticks 60 --warmups 5 --output world-profile-standard.json
```

既存出力を上書きしない。引数エラー・既存出力・出力書込失敗は終了値2、実行中の失敗はJSONに記録して終了値1、
すべての指定シナリオと保存続行が成功した場合だけ終了値0。出力先の親フォルダーは先に用意する。
`--scenario transport / battle / mixed` で一つを選べる。`--runtime path/to/mindustry_pythonista.py` で読み込む本体を明示できる。
ツールと本体の2ファイルを同じフォルダーへ置く単独実行もPCで検査する。pip・NumPy・JVM・ネットワークは不要。
Pythonistaへ持ち込む場合も本体と別の診断ツールであり、実行引数と新しい出力先が必要。実機では未実行。

`--ticks` はsteady区間の本数で8以上、`--warmups` は0以上。最初の1tickとwarmupを別記録するため、
例の総実行数は各条件 **1 + 5 + 60 = 66tick**、その後に保存復元と3tickの続行が加わる。
8未満の指定を丸めない。配置・撤去・回転の固定命令を欠落させず実行するため拒否する。

## 固定する負荷

全条件はseed 90210、既定content、平地、コア1個、明示的な初期配置を使う。
`world.sandbox=True` により自動ウェーブを止め、予定外の出現数の変化を避ける。敵・弾・設備の更新自体は省略しない。
`World.place(..., free=True)` と明示的な初期資源を用いるfixtureであり、通常の建築コストから成長させた工場ではない。

| 規模 | マップ | 輸送列 | 1列のベルト | 戦闘の砲台 | 戦闘・混合の初期敵 |
|---|---:|---:|---:|---:|---:|
| small | 48 × 32 | 4 | 10 | 6 | 24 |
| standard | 96 × 64 | 12 | 28 | 32 | 192 |

- transport: 1列はドリル→ベルト列→分配器→デュオ。コア込みの設備はsmall 53 / standard 373個。
  ドリルの初期在庫5・進捗600・warmup 1、各ベルトの初期座標0.1/0.5/0.9、分配器の銅1を明示する。
  敵0・デュオの初期弾薬0。受入先が満杯になる詰まりを含み、無限に排出する輸送能力の試験ではない。
- battle: コアとデュオのみ、計small 7 / standard 33設備。デュオ弾薬30・reload 20、固定座標へ敵を直接生成する。
  初期弾0、実際に発射した弾だけを処理する。高弾数専用や全原作ユニットの戦闘負荷ではない。
- mixed: transportと同じ配置、デュオ初期弾薬30と固定の敵を追加。元からある輸送・戦闘の暫定統合を同時に実行する。

相対tick 2で(1,1)に銅壁を配置、4で撤去。transport/mixedは6で最初のベルトを北向きへ回し、8で東へ戻す。
回転は現在のsceneアダプタと同じ `rotation` 変更＋`invalidated()` で、cargoは保持する。
配置・撤去の戻り値を検査し、実行したID・命令を各tickへ記録する。初期fixtureも実際の `World.from_dict` で検証する。

現行の幅高さ128、保存読込の敵256・弾4096、8MiBなどの暫定制限は残る。固定条件はその範囲内にあり、
指定数を黙って切り詰めたり、制限を診断ツール内だけ外したりしない。この条件の成功を超大規模への対応完了としない。
負荷の拡張と暫定上限の解消は、原作の有効な規模・ルール・メモリ管理を伴う別の実装課題。

## 時間と検査の境界

最初に実際の `World.save` で隔離一時フォルダーへ入力JSONを書き、同じファイルを `World.load` で2回読む。
通常のWorldと、インスタンスにだけ計測wrapperを付けたWorldを作る。クラスやゲームファイルを改変しない。
各tickは同じ操作を両者に適用し、**未計装step→計装stepの固定順**で測る。順番の偏り、共有PCの負荷、GC、周波数は排除していない。

計装対象は `step`、ドリル、コンベア、分配器、砲台、経路再構築、敵、弾、およびその内側の
`neighbors / mine_info / accepts / receive / offload / dump`。各メソッドで次を記録する。

- calls: 実際の呼出し回数。呼ばれなかったメソッドは `not_run` とする。
- inclusive_ns: 内側の計装メソッドを含む経過時間。
- exclusive_ns: inclusiveから直下の入れ子計装呼出し時間を差し引いた時間。
- failed_calls: 例外になった呼出し回数。途中失敗したtickは成功標本へ加えず、`failed_attempt` として残す。

全メソッドのexclusive合計はそのtickの `step` inclusiveと一致する。inclusiveを単純加算すると二重計上になる。
計装していない補助処理は最も近い計装済み呼出し元に含まれる。wrapper・時計・記録の費用は推定値で引かない。
実際に未計装のstep総時間も測り、中央値の計装/未計装比を記録する。計装時のexclusive順位だけで改善倍率を決めない。

コマンド適用、全状態digest生成・照合はstep時間の外側。通常側コマンド時間と照合時間を別記録する。
毎tickで `World.to_dict()` の全保存対象と順序を含むSHA256を比較し、さらにgrid・revision・隣接cache・
経路dirty・全距離・last_messageも比較する。保存にもこのcache列挙にもない新しいWorld属性は失敗にし、検査漏れを黙認しない。
描画・HUD・OS入力・実フレーム時間は測らない。stepの逆数をiPhoneのFPSへ換算しない。

集計はfirst / warmup / steadyと、step前のpath dirty / cleanを分け、中央値・nearest-rank p95・最大・総時間を出す。
敵がいる条件では最初のロード後と配置・撤去・回転後に経路を再構築する。warmは「再構築しない通常tick」と区別して読む。
transportは敵0なのでpath dirtyが残っていても再構築しない。dirtyというフラグだけを実際の再構築回数と取り違えない。

## 実保存と続行

測定後の未計装Worldを別の一時ファイルへ `World.save` で保存し、`World.load` で復元する。
保存時間には既存のJSON化・書込・flush・fsync・atomic replace、ロードには読込・JSON解釈・schema検証・状態構築が含まれる。
Pythonの数値モデルのメモリ内JSON比較とは違う。ツールが報告JSONを書く時間は含まない。

元のWorldと復元Worldの全保存状態が一致することを確認し、さらに同じ3tickを続行して毎tick照合する。
新しい操作命令はこの続行区間にはない。ロードは隣接cacheを空にし経路をdirtyに戻すため、
**保存続行では全保存状態を比較し、cacheの内容・revisionの同一性は要求しない**。
元Worldのwarm tickと、復元Worldの最初のcold経路再構築の時間・回数は別に記録する。

入力ファイルとcheckpointのSHA256・バイト数を記録し、終了までbytesが不変であることを確認する。
ユーザーの既存保存は読まない。完了・失敗時ともTemporaryDirectoryの後始末を呼ぶ設計である。
正式測定後の作業環境に残存があったため、全反復の実削除成功は未確認として
[統合記録](P_05_VERIFICATION_ja.md)へ分けて記した。配布へ一時入力を含めない。
保存に失敗した場合や続行が不一致の場合は試験全体を失敗にし、既に成功したtickだけを別記録として残す。
原作 `.msav`、キャンペーン共有、原作のfloat32・更新順・AI互換をこの結果から認めない。

実測で主要な処理を一つ選び、状態・順序・乱数・保存続行を保持する候補と基準を同じWorld負荷で比較する。
候補が未計装総時間を改善しなければ採用しない。数値処理の並列化、空間索引、キャッシュ等は選択肢であり、
P-05の時点で高速化成功やPythonistaでの並列実行を達成したとは扱わない。
