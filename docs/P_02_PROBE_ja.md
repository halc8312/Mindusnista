# P-02: 毎フレーム入力更新と配列保持の比較

更新日: 2026-09-10。開発用の単体比較器を拡張した。ゲーム本体は変更せず、
0.1.2-dev・Python 3.10・旧セーブ schema 1・GPL を維持する。
ここでの `probe_schema: 2` は比較記録の形式であり、ゲームの版・保存 schema の変更ではない。

## 実行方法

`tools/pythonista_parallel_probe.py` 一つを Pythonista へ置いて実行できる。ゲーム本体とは別のツール。
引数なしでは従来の P-01 を実行する。P-02 は実行引数へ `--resident` を指定する。
Pythonista へ渡す引数の例:

```text
--resident --count 20000 --warmups 2 --repeats 7
```

PC/ターミナルでの実行例:

```sh
python tools/pythonista_parallel_probe.py --resident --count 20000 --warmups 2 --repeats 7 --output p02-20000.json
python tools/pythonista_parallel_probe.py --resident --count 200000 --warmups 2 --repeats 11 --output p02-200000.json
```

出力先を省くと JSON を標準出力、日本語の結果を標準エラーへ出す。既存出力ファイルは上書きしない。
書込・flush・close の失敗時は保存成功と表示せず終了コード2を返す。
NumPy は任意の既存ライブラリで、追加インストールしない。欠如時、または `--no-numpy` 指定時は
Python だけを実行し、6つの NumPy 条件は `not_run`、全体は `partial` と記録する。
不一致・バックエンド例外・終了処理失敗は `failed` とし終了コード1を返す。

## 比較する仕事と配列の所有

入力は全条件で同じ5値の Python 行リスト、出力も全件の距離二乗・判定の2つの Python リスト。
毎フレーム全行の x を `base_x + frame / 16`、y を `base_y - frame / 32` に変える。
frame は1から始まり、他の3列は同じ。前フレームの浮動小数点誤差を蓄積せず、共通の初期値から更新する。
距離式・比較条件・件数・順序は P-01 と同じで、入力更新を含める点が P-01 の静的入力と異なる。

| 条件 | 毎フレームの処理 |
|---|---|
| Python / 1 | 行更新 → Python で全距離・判定リストを作成 |
| NumPy 都度変換 / 1・2・4 | 行更新 → 新しい入力配列 → ワーカーで作業・出力配列を生成 → 全結果をリストへ反映 |
| NumPy 配列保持 / 1・2・4 | 行更新 → 保持入力配列へ全行を代入・変換 → 保持作業・出力配列で計算 → 全結果をリストへ反映 |

配列保持では入力・dx・dy・判定のバッファを一度だけ確保し、ワーカーには重複しないビューを渡す。
dx は二乗距離の出力にも使う。全ワーカーが完了してから結果を順に反映し、次の入力を変更する。
Python 出力は独立したコピーで、後続フレームが過去の結果を上書きしない。
保持配列への代入にも Python 数値の変換費用がある。ゼロコピー、NumPy 内部の一時割当ゼロとは称さない。

## 計測区間と初期費用

すべて `time.perf_counter()` の実時間。各フレームの区間を保存する。

| JSON 項目 | 含む処理 |
|---|---|
| `prepare_seconds` | 初期行リストの保持、配列保持経路の初期変換・配列確保、executor 作成 |
| `initial_conversion_seconds` | 保持経路の最初の入力変換。prepare の内数で、二重に加算しない |
| `input_update_seconds` | 全条件共通の Python 入力行更新 |
| `input_conversion_seconds` | NumPy の新規配列化、または保持配列への全行代入・変換 |
| `compute_sync_seconds` | dispatch・計算・全 future 待機。CPU 演算だけの時間ではない |
| `result_apply_seconds` | NumPy の `tolist` と、元の順序で Python リストへ結合 |
| `runner_overhead_seconds` | 内側の区間外にある呼出し・戻り・計測辞書作成・一時オブジェクト解放 |
| `total_seconds` | run_frame の呼出しから戻りまで。上記5区間の和 |

Python はカーネル内で最終リストを作るため、その費用は compute_sync に含まれる。
Python の conversion / apply の0は結果生成を省いた意味ではない。
初回・warmup の全標本、steady の全標本・p50・p95・最大と区間別集計を保存する。
区間中央値を別々に足しても総時間中央値とは通常一致しない。和の整合はフレーム単位で検査する。

`first_with_prepare_seconds` は準備＋初回。
`amortized_seconds_per_frame` は、準備と初回・warmup・steady 全実行の総時間を、完了フレーム数で割る。
NumPy import は別記し、`amortized_including_numpy_import_seconds_per_frame` では各候補の
独立利用を想定して一度だけ加算する。初期変換を省いて有利な条件へ変えない。

参照生成・全件照合・digest・報告作成・runner 終了処理は各フレーム総時間の外。
初回を含め全実行で距離・真偽・件数を完全照合し、不一致に速度比を付けない。
途中の例外でも、それまでのフレーム記録と失敗フレームを残す。
固定実行順や各回の参照計算はキャッシュ・周波数・発熱へ影響し得る。無停止のゲームループの測定ではない。

数値バッファ概算は1件57バイト。入力 float64×5、作業兼出力 float64×2、判定 bool×1 の合計。
Python 入力・出力・参照、NumPy 内部一時領域、executor、allocator、ランタイムを含まない。
実プロセスのピークメモリは未測定で、概算を実使用量と読み替えない。

## PC で実行した結果

Linux x86_64 / CPython 3.12.14 / NumPy 2.3.5。
20,000件は初回1＋warmup2＋steady7回、200,000件は初回1＋warmup2＋steady11回。
全7条件の全フレームで全件一致し、条件ごとの参照 digest 列も一致した。
各条件の照合はそれぞれ200,000件分、2,800,000件分。テストメソッド数やゲーム世界数ではない。

| 条件 | 20,000件 p50 / p95 | 200,000件 p50 / p95 |
|---|---:|---:|
| Python 1 | 3.323 / 4.718 ms | 39.292 / 44.615 ms |
| NumPy 都度変換 1 | 7.347 / 8.472 ms | 78.574 / 86.880 ms |
| NumPy 都度変換 2 | 7.588 / 8.536 ms | 76.217 / 83.951 ms |
| NumPy 都度変換 4 | 8.885 / 9.472 ms | 76.727 / 88.321 ms |
| NumPy 保持 1 | 7.130 / 10.405 ms | 74.639 / 88.956 ms |
| NumPy 保持 2 | 7.605 / 8.556 ms | 74.885 / 97.355 ms |
| NumPy 保持 4 | 7.942 / 9.774 ms | 71.525 / 82.855 ms |

200,000件の保持4ワーカーでは、区間中央値が入力更新15.081 ms、変換51.396 ms、
計算・同期1.457 ms、反映3.505 ms。準備59.468 ms、準備込み全14回の償却は78.607 ms/回。
これらを総時間の一つの標本や同時 CPU 実行の証明としては扱わない。

**この条件では、保持方式も NumPy の全条件が Python より遅い。**
計算区間の短さだけではゲームへの加速採用を正当化できない。今回の入力境界では変換費用が大きく、
配列の再利用だけでそれは消えなかった。反復数は少なく、共有PCの他負荷・周波数も固定していない。

次はゲーム側で数値状態を配列として継続保持できる範囲を定め、入力取込・更新・必要な結果反映を
含む比較を設計する。境界や結果反映の頻度を変更する場合は、ゲームに必要な仕事との対応を先に示す。
P-02 の条件から入力や結果を省いて得た倍率を、同じ仕事量の改善と称さない。
