## 変更と採用判断

実際のWorldの採掘・搬送・戦闘・経路探索・保存を測る `tools/profile_world.py` を追加した。
予備の戦闘条件で砲台処理が最も重かったため、`World._tick_turret`の標的選択を一回走査へ変更する。
距離式・射程・ID優先順・乱数・更新頻度を保ち、候補リストと重複した距離計算を除いた。
本体の他のASTはM1-05から不変。生成・配布する.pyはこの変更を含む。

旧関数だけを同じWorldへ戻す基準との比較で、戦闘条件は3反復すべて中央値とp95が短縮した。
全状態・保存・続行の一致と、この実測を根拠に採用する。一律の高速化ではなく、輸送条件の微増や混在条件のばらつきも残す。
敵数×砲台数の全走査自体は残る。機能・規模・射程・更新頻度・効果は削減しない。
原作戦闘・float32・超大規模への対応完了ではない。
[計測境界](P_05_PROFILE_ja.md)、[同値条件と基準の由来](P_05_TARGETING_ja.md)を参照。

## 最終ソースによるPC測定

Linux x86_64 / CPython 3.12.14。96×64のstandard条件と、既存48×32の通常開始を使う。
初期戦闘は32砲台・192敵、輸送と混在は373設備（ベルト336、ドリル12、分配器12、砲台12、コア1）。
これは現行の暫定上限内の固定条件であり、原作の超大規模工場の試験ではない。

各条件3反復、各反復は初回1＋warmup5＋steady60tick。基準と候補の先行順を毎tick交代する。
表は**同じ条件の180steady標本をまとめた未計装World.step**の中央値 / nearest-rank p95（ms）。
配置操作と全結果照合は計測外。両者は同じ方法で関数をインスタンスへ束縛し、属性参照の仕組みを揃える。

| 条件 | 旧選択の中央値 / p95 | 新選択の中央値 / p95 | 解釈 |
|---|---:|---:|---|
| 通常開始（初期敵0） | 0.019395 / 0.034980 | 0.018971 / 0.033528 | 反復ごとにばらつき、安定した改善とはしない |
| 輸送のみ | 1.377414 / 2.171911 | 1.392107 / 1.885135 | 中央値は約1.1%長い |
| 戦闘 | 3.784668 / 5.970361 | 2.804693 / 4.663051 | 中央値約25.9%短縮。3反復の中央値・p95が全て改善 |
| 混在 | 3.440585 / 8.983712 | 3.008518 / 9.016767 | 中央値約12.6%短縮だが集約p95は約0.37%長い |

戦闘の反復別「候補/基準の中央値」は0.7102 / 0.7670 / 0.7630。
混在は0.8701 / 0.8686 / 1.0071で、3回目は約0.71%長い。通常開始も1.1308 / 0.9680 / 1.0389とばらつく。
共有PCの負荷・GC・周波数等は排除していない。最良値を選ばず全反復を公開し、実機FPSへ換算しない。

## 正しさ・保存・レビュー

計測器は198組、旧/新比較器は792組のtickで、全保存状態・ID順・乱数状態・非保存cacheを照合した。
旧/新の保存bytesも一致し、各反復の元/復元の計4Worldへ同じ新しい配置・撤去命令を与える36組の続行も成功。
実際のWorld.save/loadを隔離フォルダーで使い、入力とcheckpointのbytes不変を確認する。
保存前後のcache再構築は既存仕様として区別し、保存費用や復元直後のcold経路も別記録した。

計測器17本、標的選択12本の新規unittestを追加。標的選択は変更前の旧実装でも12本を通してから変更した。
既存のバグを直す差分ではなく、同じ挙動を保つ最適化なので意味的な回帰は変更前後とも成功を要求する。
射程境界・距離とID・死亡・空・弾薬・照準境界・乱数・新命令付き保存復帰、
計装の入れ子時間会計・失敗記録・±infや将来の未知状態・既存出力保護も検査する。

独立担当が固定旧関数のGitソースとのバイト一致、最小本体差分、数値条件、全標本の集計・hash・会計を確認した。
共通シナリオでは、計測器と旧/新比較器の全反復でも毎tickのdigest・命令・保存hashが一致した。
[独立レビュー](verification/P-05-20260910/review.md)を参照。

補足: 正式測定後にWorkの作業フォルダーへ残っていた合成入力・checkpointを配布対象検査で検出した。
hashは測定用fixtureと一致し、利用者の保存ではない。原本を保ってリポジトリ外へ隔離し、配布へ含めない。
コードはTemporaryDirectoryの後始末を呼ぶ設計で、追加の単独経路では終了後の残存0も確認したが、
正式JSONには各ディレクトリの消失確認がなく、今回の残存原因は未確定。全反復の実削除成功とは記録しない。
