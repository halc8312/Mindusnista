両件数の全7条件・全フレームで全件一致。200,000件の総時間中央値は Python 39.292 ms、
配列保持4ワーカー71.525 ms。保持4の変換区間中央値は51.396 msで、計算・同期1.457 msより大きかった。
今回は数値配列・作業配列の再利用を確認したが、Python リストから全行を移す変換は毎回行う。
入力変換の頻度削減、ゲームの高速化、CPU の同時実行を達成したという結果ではない。
少数反復・固定順・共有PCの観測であり、持続負荷や普遍的な性能倍率を表さない。

次は数値状態を配列として持つ構成を試し、初期取込・更新・必要な結果反映を含む実際の仕事との対応を定義する。
処理や結果を省略した測定を、同じ仕事量の高速化と称さない。現在のゲームの機能・規模・効果は削減しない。

## 保存・CI・実機の区別

各PRは実装を保存した後、対象headの GitHub CI を読み戻して実際の結果をPR本文へ記録する。
Python 3.10 / 3.13 と指定 NumPy、JDK17 の抽出コンベア比較を継続する。
CIの成功やPC測定は Pythonista 実機成功ではない。

Pythonista の比較器起動・同梱NumPy版・性能・発熱・ピークメモリは未確認。
原作 Java float32、実ゲームの状態構造、Accelerate / Metal、ゲームへの加速導入も未検証。
原作 iOS/Steam セーブ共有は S-01 以降の別課題で、今回の比較器は codec を実装しない。
