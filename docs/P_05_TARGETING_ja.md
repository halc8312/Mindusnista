# P-05: 実Worldの標的選択を一回走査へ変更

`World._tick_turret` の標的選択だけを最適化した。候補全体のリストと二度目の距離計算を除き、
射程の二乗は砲台ごとに一度、距離の二乗は生存敵ごとに一度計算する。
同じ射程内の最小 `(距離の二乗, 敵ID)` を選ぶ規則、敵の順序、全更新頻度は保持する。
これは現行の暫定戦闘処理に対する最適化であり、原作の戦闘・float32・標的予測の移植ではない。

## 選定の根拠と範囲

[実World計測器](P_05_PROFILE_ja.md) による予備測定で、standard戦闘条件のsteady 60tickでは、
計装下の排他時間合計が砲台148.320ms、弾72.001msだった。未計装のWorld.step中央値は3.863253ms。
これはボトルネック候補を選ぶ予備観測で、採用後の改善値ではない。
正式な効果・退行の判定には、以下の未計装World全体の比較を使い、結果と実行時hashを統合検証記録へ保存する。

対象は敵数×砲台数の全走査の定数費用であり、探索量のオーダーは変わらない。
敵・弾・砲台の個数、射程、更新頻度、エフェクト、描画、機能、保存上限を減らしていない。
空間索引・NumPy・CPU並列化・GPUは今回の本体へ追加していない。
Pythonistaの起動に追加ファイルや依存は不要で、配布は再生成した単体 `mindustry_pythonista.py`。
版は0.1.2-dev、schema 1、旧保存、起動ガード、GPL、固定原作v159.7を維持する。

## 同じ処理結果を維持する条件

旧版は生存敵を挿入順で調べ、`(enemy.x-x)**2 + (enemy.y-y)**2 <= spec["range"]**2` で候補を作り、
`min(..., key=(distance, id))` で一件を選んでいた。新版も座標の差・`**2`・加算の順序をそのまま使う。
乗算への置換、float32化、近似、平方根、許容誤差は導入しない。

- `hp > 0` と `distance <= range_squared` を維持する。条件を反転してNaNを選ぶ変化も避ける。
  NaN等を含む異常保存の受入を増やす変更ではなく、直接呼出しの旧挙動も試験する。
- tupleの厳密な `<` で最小値を更新する。同距離なら小さいID、同じkeyなら先に現れた対象を保持する。
- reloadの先行更新、弾薬・敵なしの早期return、旋回、発射条件、乱数呼出し、ID発行、弾生成は同じ。
- Worldの他のメソッドはこの最適化では変更しない。M1-05の分配器修正の有無を速度差へ混ぜない。

## 再現可能な旧版との比較

`tools/check_target_selection.py` は開発用で、同じフォルダーの `profile_world.py` と単体本体を使用する。
旧関数は [main 9f466b9 の app.py](https://github.com/halc8312/Mindusnista/blob/9f466b9f43fd80c172f6e6a7de9db60fac7c004d/src/mindusnista/app.py)
の `_tick_turret` を先頭の字下げと末尾改行を含めて正確に抽出した固定文字列。
SHA256は `f06cb4e4bdfafc0d418068dd17b63628cc6b8a761a2bbb6ccd132a6bcd2e8248`。
実行時にこのhashを検査してから、**現在のWorldに旧関数だけ**を差し替える。
本体の任意の旧版全体を基準へ戻す比較ではない。両者ともインスタンスへ同じ方法でメソッドを束縛し、
属性参照の仕組みを揃える。クラスを書き換えず、stepや内部メソッドへ計測wrapperを付けない。

```sh
python tools/check_target_selection.py --preset standard --scenario all --ticks 60 --warmups 5 --repeats 3 --output target-selection-standard.json
```

`--runtime` で本体を指定できる。`--seed` は初期RNG状態（既定90210）。
`--scenario normal / transport / battle / mixed`、`--preset small / standard` を指定できる。
通常開始以外の3条件は計測器と同じ `build_fixture` を使う。
normalは既存の `World.demo()`（48×32・21設備・初期敵0）のままで、presetによる拡大はしない。
sandboxはFalse、初期wave_timerは5400なので、例の66tickでは自動ウェーブはまだ始まらない。
長い試験で発生するウェーブをツール側で止めることはない。

各条件・各repeatは実際の `World.save` で作った同じ入力を2回 `World.load` して開始する。
最初の1tick、warmup 5tick、steady 60tickを分ける。tickごとに基準→候補／候補→基準の順序を交代し、
repeatの先頭順序も交代する。例の66tick全体とsteady 60tickは各repeat内で先行順が同数だが、
初回標本の先行順は3repeatなので同数ではない。各記録へ実順序を残す。
配置・撤去・回転の固定命令も計測器と同じ関数で適用し、双方の戻り値・IDを照合する。

時間を測る範囲は **未計装のWorld.step全体**。命令の適用、全 `to_dict()`・digest・cacheの比較は時間外。
各tickを照合した後だけ成功標本へ加え、最初・warmup・steadyのp50/p95・最大・合計を別記する。
全体の高速化を砲台関数だけのmicrobenchmarkから推定しない。共有PC・GC・実行順・周波数の影響は残る。
輸送・通常の退行と戦闘・混合の効果を併記し、単一標本や最良値だけで採用しない。

## 保存とその後の命令

測定後は基準・候補をそれぞれ実ファイルへ保存・再ロードし、全保存状態と保存bytesの一致を要求する。
その後、保存前の2Worldと復元した2Worldの計4状態へ同じ新しい配置・撤去命令を与え、3tick続行する。
毎tickで基準と候補の保存対象・cacheを比較し、元と復元の間では全保存対象を比較する。
復元時のcache破棄・経路dirty化は元々の仕様なので、元と復元のcache一致は要求しない。
保存・ロード時間はstep時間と分離して記録する。続行3tickは速度の採用判定へ加えない。

入力・checkpointはツール専用の隔離一時ファイルで、終了時にbytes不変を確認し、TemporaryDirectoryで後始末する設計。
正式測定後の作業環境で検出した残存と、実削除確認の限界は[統合記録](P_05_VERIFICATION_ja.md)へ記載した。
利用者の既存セーブは読まない。出力JSONは新しい名前だけを受け付け、既存出力を上書きしない。
引数不正・出力失敗は終了2、本体ロード失敗・実行途中の不一致・保存失敗・未実行tick等は終了1、全条件成功だけ終了0。
失敗した標本を成功件数に含めず、完了した標本・失敗段階・未実行項目を残す。

## 検査と残る課題

新規12 unittestを旧実装のまま成功させてから候補へ変更し、同じ12本を通した。
手計算の射程内外・射程境界、距離とIDの優先順・逆挿入順、死亡・空・弾薬なし、照準閾値の両側、
reload・乱数・弾・ID、直接渡した非有限値の除外を検査する。
3 seed×4条件で毎tickの全状態・実保存・新命令付き続行を比較し、順序交代、改変基準の拒否、
状態不一致・step/保存失敗・出力保護・一時ファイル削除、3ファイルでの単独CLIとPython3.10構文を確認する。

最適化前の統合検査はLinux / CPython3.12.14で326本（計測器17本を含む）とself-testが成功。
M1-05統合後・最終レビュー後の総数と正式性能値は別の統合検証記録を正とする。
このPC検査をiPhoneのFPS、実機の発熱・長時間性能、原作戦闘互換、超大規模対応、原作セーブ共有の成功へ転記しない。
元々の全敵走査の計算量と暫定上限は残る。今回の実測を足場に、次は空間索引等の候補削減構造を
全状態一致と実負荷で検証する。機能・正常な規模・効果を削減する対処は行わない。
